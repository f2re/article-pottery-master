# От вопроса до принятой публикации

Версия 3.1. Источник исполняемых маршрутов — `editorial/routes.json`. Девять навыков сохранены, но они не означают девять обязательных вызовов модели.

## Три профиля

`note`: один узкий вопрос; можно переиспользовать уже прочитанное досье, но проверить его применимость и новую формулировку. `standard`: самостоятельная статья, собственные материалы либо музейные источники. `research`: научная работа или повышенный риск. Тип research и риск elevated всегда включают финальную science, даже если вручную выбрали note.

Команда `python3 scripts/editorial.py route articles/<slug>` показывает порядок. В каждом профиле поиск и задача предшествуют тексту; после подготовки всех версий — замораживание и два независимых отзыва. Для research дополнительно science. Для illustrated добавляется арт-директор, его работу проверяют evidence по правам/достоверности и reader по ясности/нужности.

## Ответственность без самоприёмки

Координатор ведёт пакет и передаёт вопросы. Исследователь готовит доказательства. Автор пишет цельно. Growth сначала выбирает намерение и форматы, потом адаптирует, но не подписывает отзывы о своей адаптации. Evidence проверяет весь материал от утверждений к источникам. Reader принимает пользу, ясность, интерес, голос, SEO, версии и визуальную часть. Science до автора объясняет методы, после адаптаций проверяет окончательные научные формулировки.

Не более трёх читающих задач одновременно, один исполнитель редактирует конкретный файл. Два цикла исправлений; далее координатор возвращает владельцу свод нерешённых вопросов. После смены задания владелец может начать новый цикл с записью причины в журнале — не обнулять счётчик ради обхода проверки. Имена исполнителей и ID не являются криптографическим удостоверением личности.

## Реальный журнал

`workflow.json`:

```json
{"revision": 0, "runs": []}
```

Каждый состоявшийся запуск добавляет объект с `id`, `actor_id`, `role`, `mode`, `date`, `notes`. Роли создания: writer, growth, art; роли принятия: evidence, reader, science. `mode`: independent, human или sequential_self_review. Запись с последним режимом не может служить независимой приёмкой. actor_id — устойчивый идентификатор человека или изолированного контекста агента, run id — конкретного прохода. Не называй повторную ролевую проверку тем же агентом independent.

Журнал не создаётся автоматически из наличия файлов. В демонстрации он пуст: готовый пример не выдается за проведённую независимую редакцию. Для вспомогательных заметок есть notes/; исходники и выводы туда прятать нельзя.

## Практический сценарий

1. `init <slug>` создаёт пустой пакет с одной заметкой ВК. Заполнить задачу, источники, утверждения, текст. При нужных двух постах добавить вторую запись publications и отдельный файл; не требовать лишние форматы автоматически.
2. `check <пакет>` собирает структурные ошибки и предупреждения. `export <пакет>` создаёт черновой каталог с одним HTML-превью всех версий.
3. `inventory <пакет>` выдаёт фрагменты с ID. Независимый evidence читает их и оригиналы; reader читает весь публичный результат; science подключается согласно профилю. Каждый возвращает свой отзыв, а не правит human_approval.
4. `digest <пакет>` показывает контрольные суммы. Каждый отзыв хранит полученные при проверке content_hash и public_hash. После переноса отзывов владельцу показываются их свод и превью. Владелец сам заполняет human_approval согласно QUALITY.md.
5. `status <пакет>` проверяет выпуск; `export <пакет> --release` допускается только после него. `verify-export <экспорт> --package <пакет>` обнаруживает изменённые файлы и несоответствие текущей приёмке.

Нет фоновых процессов, вызова платной модели из Python, входа в соцсеть или отправки поста. Коды CLI: 0 — выполнено, 1 — проверка не пройдена, 2 — ошибка запуска/ввода. `status` намеренно проверяет release, тогда как `check` без флага проверяет черновик.
